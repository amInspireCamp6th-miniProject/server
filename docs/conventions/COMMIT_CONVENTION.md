# 커밋·브랜치 컨벤션

프론트엔드 레포와 같은 규칙을 사용하는 것을 목표로 합니다.
`TBD` 항목은 [DECISIONS.md](../DECISIONS.md)에서 결정되는 대로 채웁니다.

## 커밋 메시지 형식

```
<type>(<scope>): <제목>

<본문>

<꼬리말>
```

- 제목, 본문, 꼬리말은 빈 줄로 구분합니다.
- 제목만 필수이고, 본문과 꼬리말은 선택입니다.
- `(<scope>)`는 사용 여부 `TBD` ([C-04](../DECISIONS.md))입니다.

### type

| type | 설명 |
| --- | --- |
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `build` | 빌드 관련 파일, 의존성 변경 |
| `chore` | 그 밖의 자잘한 수정 |
| `ci` | CI 설정 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 스타일, 포맷 (동작 변경 없음) |
| `refactor` | 리팩터링 (동작 변경 없음) |
| `test` | 테스트 코드 추가, 수정 |
| `perf` | 성능 개선 |

### 제목

- type은 소문자로 쓰고, 콜론 뒤에 공백 한 칸을 둡니다. (`ci : ...` ✗ → `ci: ...` ✓)
- 50자 이내로 쓰고, 끝에 마침표를 넣지 않습니다.
- 한국어는 명사형으로 끝냅니다. (`~추가`, `~수정`, `~삭제`) `TBD` [C-03](../DECISIONS.md)

### 본문

- 한 줄에 72자 이내로 씁니다.
- 무엇을, 왜 바꿨는지 씁니다. 제목으로 충분하면 생략합니다.

### 꼬리말

- 관련 이슈를 적습니다: `Closes #12`, `Refs #12`
- GitHub은 기본 브랜치(`main`)에 머지될 때만 이슈를 자동으로 닫습니다. `develop`에 머지할 때는 이슈를 직접 닫아야 합니다.

### 예시

```
feat(ingredient): 소비기한 임박 식재료 조회 API 추가

소비기한이 가까운 순으로 정렬해 반환한다.
만료된 식재료는 /ingredients/expired 에서 따로 조회한다.

Closes #12
```

```
fix: 대시보드 만료 식재료 수 계산 오류 수정
```

## 브랜치 전략

백엔드 3인 기준으로 고정합니다. (D-14)

```
feat/*, fix/*  →  develop-<이름>  →  develop  →  main
  (작업)           (개인 통합)       (개발 통합)   (배포)
```

| 브랜치 | 용도 | 예시 |
| --- | --- | --- |
| `main` | 배포 가능한 상태 | |
| `develop` | 개발 통합 | |
| `develop-<이름>` | 개인 통합 브랜치 (인원수만큼) | `develop-ham` |
| `feat/<기능>` | 기능 개발 | `feat/ingredient-crud` |
| `fix/<내용>` | 버그 수정 | `fix/expiration-dday` |
| `chore/<내용>`, `docs/<내용>` | 설정, 문서 작업 | `docs/api-spec` |

### 브랜치 이름 규칙

- **소문자와 하이픈(`-`)만 사용합니다.** 밑줄(`_`)이나 대문자는 쓰지 않습니다. (`feat/ingredient-crud` ○ / `feat/Ingredient_CRUD` ×)
- 슬래시(`/`)는 종류를 나누는 접두사에만 씁니다. (`feat/`, `fix/`, `chore/`, `docs/`)
- 한글은 쓰지 않습니다. 환경에 따라 글자가 깨질 수 있습니다.
- 접두사와 같은 이름의 브랜치는 만들 수 없습니다. `feat` 브랜치가 있으면 `feat/xxx`를 만들 수 없습니다. (Git이 `feat`을 폴더처럼 다룸)
- 대소문자만 다른 브랜치는 만들지 않습니다. Windows와 macOS에서는 같은 이름으로 취급되어 충돌합니다.
- 이슈 번호를 붙이려면 종류 뒤에 둡니다. 예: `feat/12-ingredient-crud`

### 흐름 규칙

- 작업 브랜치(`feat/*`, `fix/*`)는 **자신의 `develop-<이름>`에서 만들고** 다시 그 브랜치로 머지합니다.
- `develop-<이름>` → `develop` → `main` 순서로만 올립니다. 건너뛰지 않습니다.
- 역방향 머지(`main` → `develop`, `develop` → `develop-<이름>`)는 하지 않습니다.
  - 다른 사람 작업을 받아야 하면 `git pull`로 최신 `develop`을 받은 뒤 자신의 브랜치에서 rebase합니다.
- `develop-<이름>`은 머지 후에도 남겨 두고 계속 씁니다. `feat/*`, `fix/*`는 머지 후 삭제합니다.
- 예외: 프로젝트 초기 세팅은 작업 브랜치에서 `main`으로 직접 머지했습니다. 그 뒤 `develop`과 개인 브랜치를 `main` 위치로 fast-forward 했습니다. (D-15)
- 원격 변경을 받을 때 불필요한 머지 커밋이 생기지 않게, 각자 로컬에 한 번 설정합니다.

  ```bash
  git config pull.rebase true
  ```

## 머지 방식

머지는 팀원이 직접 진행합니다. (D-13)

- 자동 머지 설정이나 GitHub 규칙 세트로 머지 방식을 강제하지 않습니다.
- 머지 방식과 관계없이 **모든 커밋에 위 규칙이 적용**됩니다. 커밋 메시지를 자동으로 검사할지는 [C-19](../DECISIONS.md)에서 정합니다.
- `develop` → `main` 머지는 이력을 남기기 위해 merge commit 방식을 권장합니다. squash로 머지하면 두 브랜치의 이력이 어긋나 다음 머지에서 충돌이 생깁니다.
